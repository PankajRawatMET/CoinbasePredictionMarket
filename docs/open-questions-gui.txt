CPM GUI - OPEN QUESTIONS (Stage G0)
===================================
Raised 2026-10-28, from the GUI brief: the app runs on an AWS Linux instance
reached from Windows over PowerShell or cmd, and running it should print a
localhost link the operator opens in a browser. Same format as
docs/open-questions.txt and docs/open-questions-oms.txt: each entry carries the
question, the reference, and the proposed answer, which is what gets built
unless you say otherwise.

You said "go with defaults", so every entry below that had a proposal is marked

GUI-Q1  One process per strategy, or one daemon hosting many?
-----------------------------------------------------------------------------
Question : "Start strategies from the GUI" could mean the GUI spawns a
           crypto_mm process per strategy, or one long-lived daemon hosts them
           all. The first is simpler and isolates crashes.
Spec ref : OE:197-201 "Each FIX session maps 1-to-1 to a registered trading
           user. The user is resolved from SenderCompID(49), which is the API
           key... A second Logon for the same user disconnects the first
           session with Logout(5), Text(58)='replaced by newer connection'."
           OE:1337-1339 "When a newer connection for the same API key replaces
           this session, the API key is still live, so no cancel-on-disconnect
           is triggered - the replaced session's orders remain."
Answer   : RESOLVED by the spec - process-per-strategy is not merely untidy,
           it is unsafe. Starting a second strategy would displace the first
           strategy's session, and because cancel-on-disconnect does not fire
           on a replacement, the first strategy's quotes would be left resting
           in the market with no process managing them. The code already knows
           this: cpm::oms::SessionEvent::Kind::Replaced and
           cpm::oms::Halt::Reason::Replaced exist for exactly this event.
           One daemon, many strategies. See docs/design-gui.md section 2.
           This also settles the state question: one OrderState, one position
           per symbol and one bookmark file, none of which two processes could
           share ([OMS] OE-Q7).

GUI-Q4  Does the daemon exit on a halt, or stay up to explain itself?
-----------------------------------------------------------------------------
Question : Instructions amendment 4 is fail-stop: on a gap, a stale feed or
           any reject, report a terminal halt and stop the session. crypto_mm
           implements that by returning 4 from main(). If the daemon does the
           same, the browser loses its connection at the moment the operator
           most needs to read why.
Ref      : instructions amendment 4; [MD] Q24/Q25/Q27/Q28; [OMS] OE-Q6.
Proposal : Keep fail-stop exactly as it is for trading - withdraw every
           strategy, close the submission gate, flatten and reconcile per
           OE-Q6, stop both FIX sessions, refuse every start and arm - but do
           not exit the process. It stays in a terminal Halted state serving
           the page read-only, so the halt reason, the last book, the
           positions and which strategy held what are all still readable. No
           "clear halt" control exists; the only way out is to shut the daemon
           down and start a new one.
           This is strictly weaker than exiting in one respect only: the
           process lingers. It is strictly stronger in that a halt at 02:00
           leaves something to read instead of an exit code on a closed
           PowerShell window.
Status   : DEFAULTED 2026-10-28. Say so if you would rather it exit.

GUI-Q10 OrderLimits were sized for one strategy, not N
-----------------------------------------------------------------------------
Question : crypto_mm sets OrderLimits per run: max_orders_per_sec = 4, sized
           for "two sides, a few re-quotes", and max_quantity = 2x the
           strategy's own quantity. OrderLimits lives on the OeClient, so in
           the daemon it is shared by every strategy. Four orders a second
           across five strategies is one re-quote each per 1.25 s, and the
           limit silently becomes the binding constraint on all of them.
Ref      : cpm::oms::OrderLimits in order_management/include/cpm/oms/oe_client.hpp;
           strategies/CryptoMM/apps/crypto_mm/main.cpp sets them per run.
Proposal : The daemon owns the limits and recomputes them as strategies are
           created and destroyed: max_orders_per_sec as a configured daemon
           ceiling (--max-orders-per-sec, default 8) rather than a sum, since
           a rate limit is a property of the session; max_quantity and
           max_notional as the maximum over the live strategies rather than
           the sum, because they are per-order caps, not exposure caps. The
           GUI shows the limits in force and whether anything is being
           throttled by them, because a strategy quoting less than it should
           and not saying why is the failure mode the CryptoMM design already
           spent a section avoiding.
           Note what these are not: not a risk engine, and not exposure
           limits. max_inventory per strategy remains the only position cap,
           and it stays per strategy.
Status   : BUILT 2026-10-28 (G2), with one change from the proposal. All three
           limits are daemon flags (--max-order-qty, --max-orders-per-sec,
           --max-notional) rather than a maximum over the live strategies,
           because IStrategy deliberately does not expose a quantity: asking a
           strategy how large its orders are would put kind-specific knowledge
           back into the host, which is exactly what the schema seam removed.
           The GUI shows the limits in force (ControlApi LimitsView).

GUI-Q2  Toolkit
-----------------------------------------------------------------------------
Question : Qt, Dear ImGui, a terminal UI, or a browser page served by the
           daemon?
Note     : The instance has no GUI toolkit installed at all - no Qt, no GTK,
           no GLFW, no SDL, no pkg-config, no node - and reaching it from
           Windows over SSH means a native window would need X11 forwarding.
Proposal : A browser page served over localhost HTTP. It is the only option
           that adds no third-party dependency (sockets, plus OpenSSL which is
           already linked) and the only one visible from Windows without
           extra software. docs/design-gui.md section 1 records what was
           rejected and why.
Status   : DEFAULTED 2026-10-28.

GUI-Q3  Bind address, port and authentication
-----------------------------------------------------------------------------
Question : What does the server listen on, and what stops someone else using
           it? It can start and arm trading strategies.
Proposal : 127.0.0.1 only, never 0.0.0.0, with no option to change it - the
           operator reaches it through an SSH local forward, so SSH is the
           authentication and the encryption. Default port 8080, --port to
           change it, a clear error naming the port when it is already taken
           (a stale daemon holding it is the obvious first failure). A
           per-run token, 16 hex characters from OpenSSL RAND_bytes, required
           on every request as Authorization: Bearer or ?t= on the page load;
           the page stores it and strips it from the address bar. The token
           is what keeps another user on the same instance out, which a
           loopback bind alone does not do.
           Explicitly not built: TLS on the HTTP surface (the tunnel has it),
           any login, any multi-user notion.
Status   : DEFAULTED 2026-10-28.

GUI-Q5  Who owns the durable bookmark now?
-----------------------------------------------------------------------------
Question : [OMS] OE-Q7 allows order management exactly one durable file, the
           last processed ExecID plus the ClOrdID counter, and crypto_mm
           passes --bookmark for it. With one daemon and N strategies, whose
           file is it?
Proposal : The daemon's, not any strategy's: one Reconciler, one bookmark,
           --bookmark on cpm_trader with the same default. Nothing about
           OE-Q7 changes except which binary names the path - there is still
           exactly one durable file, which is the point of the rule. A
           strategy cannot ask for its own, and the GUI cannot set the path.
Status   : DEFAULTED 2026-10-28.

GUI-Q6  Two strategies on the same symbol
-----------------------------------------------------------------------------
Question : Allowed, or refused? Two quoters on one instrument cross each
           other's quotes, and they share one position, so each one's
           max_inventory check sees the other's fills as its own.
Proposal : Refused at create time, with the reason shown in the GUI. The
           position is per symbol in OrderState and cannot be attributed
           between two strategies, so max_inventory would be meaningless for
           both. Different symbols, any number.
Status   : DEFAULTED 2026-10-28.

GUI-Q7  Does crypto_mm the CLI survive?
-----------------------------------------------------------------------------
Question : Once CryptoMM runs under the daemon, is the standalone binary
           still built?
Proposal : Yes, with the same flags and the same behaviour, reimplemented on
           IStrategy. Its existing tests are the regression that proves G1
           refactored rather than rewrote, and a one-shot dry run from a shell
           stays the quickest way to ask "what would this quote right now".
Status   : DEFAULTED 2026-10-28.

GUI-Q8  How does the page reach the browser?
-----------------------------------------------------------------------------
Question : Served from a file on disk, like the dictionaries in config/, or
           embedded in the binary?
Proposal : Embedded at build time - the .html stays a real editable file in
           gui/web/, and CMake turns it into a C++ string literal. No runtime
           asset path to get wrong, and no file-serving code path, so no path
           traversal to review. The server serves exactly one document and
           one API; it is not a web server.
Status   : DEFAULTED 2026-10-28.

GUI-Q9  Delta stream or snapshot polling?
-----------------------------------------------------------------------------
Question : How does the page stay current - polling /api/snapshot, or a push
           stream?
Proposal : Server-Sent Events, with a full snapshot as the first event on
           every connect and after every reconnect. SSE over WebSockets
           because the traffic is one-way, SSE is a few lines of HTTP rather
           than a framing implementation, and the browser reconnects it
           without help. Snapshot-first because an operator closing a laptop
           and reopening it later is the normal case on this setup, not the
           exception.
Status   : DEFAULTED 2026-10-28.

GUI-Q11 Arming versus the reconciler's gate
-----------------------------------------------------------------------------
Question : Should arming a strategy be refused while the reconciler is still
           reconciling? The first G2 build folded both into one predicate, so
           it was - and the refusal read "the daemon is not allowing orders
           (start it with --allow-orders)" even though --allow-orders had been
           given. Clicking Arm a second after startup would have hit it.
Ref      : cpm::oms::Reconciler::submission_allowed(), which is false in
           RecoveryState::Reconciling on every logon ([OMS] OE-Q6).
Answer   : RESOLVED 2026-10-28 (G2). They are two different questions and now
           have two hooks. StrategyHooks::orders_permitted is the static
           --allow-orders key and is the only thing arming consults;
           StrategyHooks::can_submit stays dynamic (permitted AND armed AND
           reconciled AND not halted) and is what actually holds an order
           back. Reconciliation is a reason to wait, not a reason to refuse
           the operator's intent. So a strategy can be armed immediately and
           simply quotes nothing until the gate opens, which is visible in the
           snapshot as "running ARMED" with "recovery reconciling".

GUI-Q12 What claims a symbol, and what frees it
-----------------------------------------------------------------------------
Question : GUI-Q6 refuses two strategies on one symbol. Refuses it against
           what - the running strategies, or every strategy that exists?
Note     : The first G1 build checked only the non-stopped ones, which was no
           check at all: a strategy is Stopped the moment it is created, so two
           could be created on one symbol and then both started. It would also
           have let destroy() unsubscribe a symbol out from under the other
           claimant, since ControlApi unsubscribes on remove.
Answer   : RESOLVED 2026-10-28 (G1/G2). A symbol is claimed by any strategy
           that exists, whatever its run state. Freeing it means removing the
           strategy, which is only possible once it has stopped. Stopping
           alone keeps both the claim and the subscription, which is also what
           an operator restarting something expects.

GUI-Q13 Does stopping a strategy disarm it?
-----------------------------------------------------------------------------
Question : stop_all() and halt() disarm everything. Should an individual stop
           do the same, or leave the arming in place so a restart resumes?
Answer   : RESOLVED 2026-10-28 (G2). It disarms. Otherwise a strategy
           restarted later would begin trading at once on the strength of an
           arming done before whatever made the operator stop it, with no
           second confirmation - and G5 is adding a confirm-on-arm step that
           this would quietly bypass. Restarting therefore needs arming again.

GUI-Q14 Does the stream send deltas, or whole snapshots?
-----------------------------------------------------------------------------
Question : GUI-Q9 settled on SSE with a snapshot first and "then deltas". What
           does a delta mean for this payload, and is it worth having?
Ref      : docs/design-gui.md section 7; cpm::trader::Snapshot.
Answer   : RESOLVED 2026-10-28 (G3). Whole snapshots, one per change and at
           most one per 250 ms pass, each as an `event: snapshot` carrying the
           revision as its SSE id. A snapshot of a daemon running five
           strategies is a few kilobytes over loopback, so a delta protocol
           would save nothing measurable and would cost the property that
           matters at 02:00: with no merging in the page, there is no way for
           what the browser shows and what the daemon holds to drift apart,
           and a missed event cannot leave a stale leg on the screen. A
           `: keepalive` comment every 15 s keeps a dead tunnel from reading
           as a quiet market. If a future snapshot ever grows past a few tens
           of kilobytes - a hundred strategies, or depth in the books - this
           is the decision to revisit, and the revision on every event is
           what a delta protocol would need anyway.

GUI-Q15 P&L
-----------------------------------------------------------------------------
Question : The GUI brief asks the control panel to show P&L. Nothing in the
           daemon computes one.
Ref      : cpm::trader::PositionView (net, bought, sold, cash, fees, fills,
           settlement_payout); cpm::trader::BookView::mid.
Note     : Realized P&L is derivable from what is already in the snapshot -
           cash less fees, plus the settlement payout once a window settles.
           Unrealized needs a mark, and the only honest one here is the mid,
           which is absent exactly when the book is invalid or one-sided.
           Rendering that as zero would show a flat position where the truth
           is "not known", which is the failure the CryptoMM design spends a
           section avoiding.
Status   : DEFERRED 2026-10-28 by the operator ("leave pnl for now"). Not
           built in G3 or G4. When it is wanted: a PnlView per symbol and a
           daemon total, realized and unrealized separately, unrealized null
           rather than zero when there is no mid, all as scaled integers like
           everything else that crosses to the browser.

GUI-Q16 What stops another page on the same browser from driving the daemon?
-----------------------------------------------------------------------------
Question : GUI-Q3 settled the bind and the token. A browser is a shared
           client: a page on any other site can issue requests to
           http://localhost:8080 from the operator's own browser.
Ref      : gui/src/server.cpp (the Host guard, the token, the CSP header).
Answer   : RESOLVED 2026-10-28 (G3). Three things, none of which replaces the
           others. The token is required on every request including the
           stream, and a cross-site page cannot read it. The Host header must
           name localhost, 127.0.0.1 or ::1, so a hostile name that resolves
           to 127.0.0.1 - the DNS rebinding route to a loopback server - is
           refused with 403 even with a token. And the page is served under a
           Content-Security-Policy that lets it load nothing at all, so there
           is no third party in the document to steal a token from. Token
           comparison is constant time: another user on the same instance can
           otherwise time a loop that stops at the first wrong character.

GUI-Q17 When should the page stop saying "reconnecting"?
-----------------------------------------------------------------------------
Question : EventSource retries a dropped stream by itself, forever. A token
           the daemon will never accept produces exactly the same retry loop
           as a flaky tunnel, and in both cases the page goes on showing the
           last snapshot it received as though it were now.
Ref      : gui/web/index.html (GIVE_UP_AFTER, giveUp, the heartbeat listener);
           gui/src/server.cpp (the heartbeat event, the retry hint).
Answer   : RESOLVED 2026-10-28 (G5). Three parts. The daemon's keepalive
           became a named `heartbeat` event rather than an SSE comment,
           because a comment keeps a connection warm but is invisible to the
           page - so the page can now tell a quiet market from a dead tunnel,
           which is the distinction that matters at 02:00. It carries the
           revision, so a page that missed an update reconnects for a whole
           snapshot instead of merging. The daemon also sends its own
           `retry: 2000`, so the reconnect delay is its decision rather than
           whichever browser it is. And after five failures with nothing
           received in between, the page stops claiming to reconnect: it dims
           every number, marks the state "last known", and offers Reconnect.
           Showing the past as though it were the present is the failure this
           whole stage exists to prevent.

GUI-Q18 What keeps the kill switch pressable?
-----------------------------------------------------------------------------
Question : Stop All is the control that matters when everything else has gone
           wrong, which is exactly when a page is most likely to be stuck.
           The first G4 build disabled it whenever a request was in flight.
Ref      : gui/web/index.html (act's `always`, REQUEST_TIMEOUT_MS, the startup
           path); gui/tests/page_test.cpp KeepsTheKillSwitchReachable.
Answer   : RESOLVED 2026-10-28 (G5). Four ways it could have become
           unreachable, each closed: it is never disabled; it is never queued
           behind another request; every request carries a ten-second deadline
           so the busy flag cannot stick on a daemon that accepts a connection
           and then stops answering; and the stream is opened whether or not
           the schema could be read, so a failed schema costs the create form
           and nothing else. Cancels are never gated below this either - the
           order client has always exempted them (OE-Q6) - so stopping works
           at every layer it passes through.

GUI-Q19 What does a ladder show on a venue with no asks?
-----------------------------------------------------------------------------
Question : The operator asked for a Ladders section: the full book per symbol
           with our own orders highlighted. But this venue quotes two stacks
           of bids - YES and NO - and no asks at all ([MD] Q9), so "the book"
           has no single price axis to put a ladder on.
Ref      : cpm::md::InstrumentView::yes / ::no; cpm::trader::LadderLevel;
           gui/web/index.html renderLadders.
Answer   : RESOLVED 2026-10-28. One axis, in YES terms. The daemon sends the
           YES stack as the bid rungs and turns each NO bid into the YES ask
           it implies (one minus the price) before sending it, so the page
           does no arithmetic on a price - the subtraction happens in scaled
           integers where every other price calculation in this system
           happens. Each ask rung also carries venue_price, the NO bid the
           venue is actually holding, so this screen can be checked against
           the venue's own.
           Three smaller decisions that go with it. Every price crosses the
           wire twice, as formatted text and as an exact tick count, because
           the page has to order rungs and match an order to one and doing
           either on "0.585" would mean parsing a decimal in JavaScript. An
           order of ours at a price the book does not show - deeper than the
           subscription, or not echoed back - still gets its own rung, since
           not seeing your own order is the one thing a ladder must never do.
           And two orders on one rung are listed ("2+1") rather than summed,
           because adding two formatted quantities in the browser is the
           arithmetic this page is not allowed to do.
           Depth is whatever the subscription asked for: cpm_trader gained
           --book-depth (1 or 10, as the spec allows), default 10.

GUI-Q20 What wakes the stream?
-----------------------------------------------------------------------------
Question : push_events() sent a snapshot when ControlApi's revision changed.
           The revision counts operator actions - create, start, arm, stop.
           What about everything else the daemon does?
Ref      : gui/src/server.cpp push_events(); ControlApi::bump();
           gui/tests/live_test.cpp TheStreamFollowsTheMarketAndNotJustTheOperator.
Answer   : RESOLVED 2026-10-28, and it was a bug, not a question. A book that
           moves, a quote that is re-placed and a fill that arrives all reach
           the daemon without touching ControlApi, so none of them bumped the
           revision and none of them reached a watching browser. A page
           therefore froze on the last button its operator pressed: the
           ladder showed quotes that had long since been cancelled, and a
           strategy armed before its first quote existed showed no orders at
           all, for ever. It survived G3, G4 and G5 because every test either
           asserted immediately after an action or re-read /api/snapshot,
           which is always fresh - the stream was the only stale thing, and
           nothing watched it idle.
           The fix: the daemon renders its state on a timer (--refresh, 500
           ms) and sends it to any connection whose last payload differs.
           Identical state sends nothing, and the heartbeat still covers
           saying nothing. The regression test watches a stream for several
           seconds without asking the daemon for anything and requires both
           the book and the strategy's own quotes to change while the
           revision does not.

GUI-Q21 One page or several?
-----------------------------------------------------------------------------
Question : G4 put the strategy table, the start form, the books, the ladders
           and the positions on one scrolling page. At what point is that too
           much to read at 02:00?
Answer   : RESOLVED 2026-10-28 at the operator's request. Four pages behind a
           nav - Strategies, Ladders, Books, Positions - with a count beside
           each name so a page nobody is looking at can still report itself.
           The view is the URL fragment, so it survives a reload and can be
           sent to someone; stripping the token from the address bar keeps it.
           What stays above the nav, on every page: the daemon state, both

GUI-Q22 How much of the price range does a ladder show?
-----------------------------------------------------------------------------
Question : The first ladder (GUI-Q19) drew only the rungs the book had depth
           at, so it changed height as the market moved and showed nothing
           about where a price could be. The operator asked for the complete
           ladder, 0 to 1.
Ref      : cpm/md/ticks.hpp price_grid(); GET /api/ladder; gui/web/index.html.
Answer   : RESOLVED 2026-10-28. The whole axis, every price the instrument's
           tick grid allows, ends included. Three things followed from it.
           First, the grid moved out of CryptoMM into cpm/md/ticks.hpp: it is
           a property of the instrument - what an order may be priced at -
           and a ladder needs it as much as a strategy does. CryptoMM keeps
           its own names by alias and its 25 tests are unchanged.
           Second, membership is not stepping. tick_at(0.900) returns the
           coarse tick because that is where a strategy stepping up from
           0.900 lands, but 0.901 is a price an order can rest at, so the grid
           contains it. price_grid() is built by region for that reason, and
           the tapered grid has 281 rungs rather than the 272 a walk would
           give.
           Third, the axis is its own endpoint. It never changes while the
           instrument exists, and sending 281 rungs twice a second to say the
           same thing would be most of the stream's bytes, so the page asks
           once per symbol - the same pattern as the parameter schema.
           What the page does with it: builds each ladder once and updates the
           cells in place, keeps rungs for prices seen off the grid, centres
           on the market the first time it has a height to centre in, and then
           leaves the scroll where the operator put it.

GUI-Q23 The venue's grid is not one the spec lists  *** NEEDS YOUR EYES ***
-----------------------------------------------------------------------------
Question : The operator states the venue's grid as: prices are a percentage
           chance from 0 to 100; the tick size is 0.1 between 0 and 1 and
           between 99 and 100, and 1 everywhere else. So the rungs run
           0, 0.1, 0.2 ... 0.9, 1, 2, 3 ... 98, 99, 99.1 ... 99.9, 100.
Spec ref : docs/open-questions.txt O5, from the REST spec section 6.4
           "PriceLevelStructure", which lists exactly three structures:
             LINEAR_CENT        0.00-1.00  tick 0.01
             DECI_CENT          0.00-1.00  tick 0.001
             TAPERED_DECI_CENT  0.00-0.10  tick 0.001
                                0.10-0.90  tick 0.01
                                0.90-1.00  tick 0.001
Conflict : None of the three is what was described, though it is close to the
           third. In the spec's units the operator's grid is 0.01 ticks with
           0.001 ticks below 0.010 and above 0.990: the same shape as
           TAPERED_DECI_CENT, which tapers below 0.100 and above 0.900 - ten
           times as far in from each end. 119 rungs against 281.
Decision : BUILT as described, as a fourth structure named tapered-cent, and
           made the default for both the daemon (--tick-structure) and
           CryptoMM's schema. It was briefly called cent-top, before the
           bottom of the grid was described; that spelling is still accepted
           so a saved command line keeps working.
           Instructions amendment 2 says the spec wins over the instructions,
           so this is flagged rather than quietly taken: the
           operator is describing the venue they are trading, and the PDF may
           be stale or may describe a different series. The three spec
           structures are all still selectable and unchanged.
           CONFIRMED 2026-10-28, over REST, and it is TAPERED_DECI_CENT:
             GET /api/v1/instruments?series_ticker=BTCD15M&status=OPEN
             -> price_level_structure "TAPERED_DECI_CENT"
           The same for ETHD15M. See
           docs/spec/capture-rest-20261028T1205-instruments.txt. The venue
           therefore disagrees with the description tapered-cent was built
           from: it tapers from 0.100 and 0.900, not from 0.010 and 0.990.

           Nothing breaks, and it is worth being exact about why. Every price
           on tapered-cent is also on TAPERED_DECI_CENT - 119 rungs inside
           281, a strict subset - so no order is ever priced between the
           venue's rungs and there is no reject to fear. What is lost is
           resolution, in two bands: from 1.1% to 9.9% and from 90.1% to
           98.9% the venue has a rung every tenth of a point where
           tapered-cent has one every point. The cost is that the ladder
           marks 162 real prices "off-grid" when the book uses them, and the
           strategy quotes a point at a time in the tails where it could
           quote a tenth. Neither halts anything; both are wrong on screen.

           Decision: the default becomes tapered once R1b reads
           price_level_structure per instrument, which removes the guess
           altogether - the venue states the grid and --tick-structure
           becomes the fallback for an instrument REST was not asked about.

GUI-Q24 Prices on the screen are a percentage chance
-----------------------------------------------------------------------------
Question : The GUI showed 0.599, the wire's units. The operator reads a
           prediction market as a chance: 59.9.
Answer   : RESOLVED 2026-10-28. Every price the GUI shows is a percentage -
           the ladder's axis, the books table, a strategy's live orders, the
           arm dialog, the spread and the mid - and the snapshot carries
           "price_unit":"percent" so the page never has to assume it. There is
           no conversion anywhere: a price is already thousandths of one, so
           the percentage is the same integer formatted with one implied
           decimal instead of three (format_percent). Nothing passes through a
           double, and price_ticks beside every price is still the raw scaled
           integer the page orders and matches on.
           Deliberately not changed: the daemon's logs, the stdin console and
           every FIX message keep the wire's units, because that is what the
           venue and the capture files use and a log that disagreed with a
           capture would be worse than one that disagrees with the screen.

           Two things made it fit. The one-line help under each input is the
           input's tooltip now, and every control in the row is one height,
           selects included, so the labels sit on one baseline.
           Labels are the operator's words, not the flags': a label is
           title-cased from the name ("max-inventory" -> "Max Inventory")
           unless the schema gives one, which is how width-ticks shows as
           "Spread". ParamSpec::label carries it, so the page still knows
           nothing about CryptoMM (design-gui §4). The wire name never moves:
           --width-ticks, the stdin console and the arm dialog are unchanged,
           and a saved command line keeps working.
           2026-10-29, same day: the table above the row is GONE and the row
           is the whole section. Every strategy is a row of the same shape -
           five buttons (Start Feed off, because its feed is up; Start; Stop;
           Arm/Disarm; Remove), its parameters shown and disabled, and one
           line under it with state, armed, id, series, window, live orders,
           placed/cancelled/fills and why. The blank row at the bottom is the
           only one that creates; when its symbol already has a strategy the
           three refuse and point at the row above, so one strategy never has
           two sets of controls.
           Chosen over a single row with the others as chips, and over a
           single row and nothing else: a strategy running and armed where
           the page does not show it is the one thing on this screen that is
           actually dangerous.
           Arm keeps its confirmation dialog (GUI-Q8), now on the row.
           A live row's parameters are disabled - they are fixed for the life
           of an instance - and its symbol comes off the live subscription,
           so a series strategy shows the window it is on now.
           The three are the daemon's own verbs, not new ones:
             Start Feed  POST /api/strategies - creates the strategy, which
                         subscribes its book and leaves it stopped and
                         disarmed. That is the feed, on its own.
             Start       .../start, and creates first if nothing is there to
                         start, so one press is enough from an empty form.
             Stop        .../stop. The feed stays up: only Remove
                         unsubscribes (ControlApi::destroy).
           They act on whichever strategy is already on the kind and symbol
           the form shows - a symbol belongs to one strategy (GUI-Q6), so
           that is a key, and it needs no state in the page: it still answers
           after a reload, and retyping the symbol moves the buttons to the
           strategy that name belongs to, or back to creating one.
           Arming stayed in the table. It is the only control that can put an
           order in the market and it keeps its confirmation; a strip that
           could arm by itself would undo GUI-Q8.
           One thing had to be fixed to make this usable at all: the form was
           rebuilt from its defaults on every snapshot, twice a second, which
           moved the caret and wiped half-typed values. The fields are now
           built once per kind and only the strip is redrawn.

GUI-Q26 Three buttons, no Arm, no Remove, and rows that are asked for
-----------------------------------------------------------------------------
Question : The operator wants no Arm and no Remove button; Start should
           start quoting; blank rows should be added on request rather than
           always being there; and the Symbol box should show the series
           (BTCD15M) rather than the window it resolved to.
Answer   : RESOLVED 2026-10-29. Every row, live or blank, has Start Feed,
           Start, Stop and nothing else.
           **Start arms.** It creates what is missing, starts it and arms
           it, in that order. This reverses half of GUI-Q8: arming is no
           longer a second key the operator turns separately. What is kept
           is the confirmation - Start opens the same dialog, now headed
           "Start quoting <symbol>?", naming the strategy, the symbol, the
           parameters, the per-order limits and the recovery state, and
           nothing is sent until it is confirmed. The daemon-wide
           --allow-orders key is untouched, and without it Start is a dry
           run and does not ask, because nothing can reach the venue.
           FLAGGED: one confirmed press now puts live orders in the market
           where it used to take two deliberate acts. The operator asked for
           this directly and it is their screen; it is written down here
           because GUI-Q8 said the opposite.
           **Nothing on the page destroys a strategy.** `destroy` is still
           in ControlApi and on the stdin console, but no button calls it,
           so the page can no longer unsubscribe a book: a stopped strategy
           keeps its feed and its row for the life of the daemon. Known
           consequence, accepted: rows accumulate across a long session, and
           `evict_finished()` (GUI-N3) is what keeps the memory bounded.
           **Blank rows are added, not conjured.** `Add row` sits under the
           rows. A blank row carries a `×` that throws the blank row away -
           it is not the Remove button, and a row with a strategy behind it
           does not have one. On Start or Start Feed the blank row goes,
           because the strategy's own row takes its place.
           **The Symbol box shows the series.** The snapshot carries
           `series` beside `target` and `symbols`: the target if it follows
           one, else parse_ticker's series, else the first dash-separated
           field, which is what the simulator's own tickers fall back to.
           The window it is on now is on the line under the row, where it
           changes every quarter hour without the row moving.

GUI-Q27 A log panel on the page
-----------------------------------------------------------------------------
Question : The operator wants the important log lines on the page, in a
           panel at the bottom, scrolling both ways.
Answer   : RESOLVED 2026-10-29. `cpm::LogRing` is a bounded tail (500 lines)
           that `Logger::also_to` feeds under the same lock as the write, so
           the panel and stdout can never disagree about the order. Each
           line carries a sequence number.
           **The raw FIX traffic is left out** below Warn: it is the bulk of
           what this daemon writes, the stdout log is where it belongs, and
           a panel scrolling past at thirty lines a second would hide the
           one line an operator is looking for. Everything else goes in,
           including QuickFIX's own session events.
           It travels as its own SSE event, not in the snapshot: the
           snapshot is re-sent whenever anything moves, and the tail of a
           log would be the same hundreds of lines every pass. Each
           connection remembers what it has been sent, so a page that joins
           late gets the tail and a page that has been watching gets only
           what is new. A reconnect re-sends the tail, and the page drops
           what it already has by sequence number.
           The panel is `white-space: pre` and scrolls both ways, because a
           wrapped log line hides the shape of the thing being read. It
           sticks to the bottom only when the operator is already there.

GUI-Q28 A controls section that holds still, and a panel of events
-----------------------------------------------------------------------------
Question : The operator wants the log panel on the Strategies page only and
           pinned to the bottom of the window; nothing in the Run a strategy
           section to update by itself; and the panel to carry the events
           that matter, not the requoting.
Answer   : RESOLVED 2026-10-29.
           **The panel is a section of the Strategies view** and carries
           data-view like any other, so the nav hides it with the rest of
           that view. It is position:fixed at the bottom of the window, and
           that view's main reserves the room under it (body[data-page]).
           **The row holds still.** The live orders and the
           placed/cancelled/fills counters came off it: they were the only
           things on a controls section that moved twice a second, and they
           are on Ladders, Books and Positions where they belong. What is
           left - state, armed, id, series, window, and why it is not
           quoting - changes when the operator acts, when it rolls, or when
           it stops, and it must: a strategy that halted and did not say so
           would be the worst thing on this page.
           The rows are also rebuilt only when that text differs, rather
           than on every snapshot. Nothing flickers under the pointer, and
           twice a second the page now does nothing to this section at all.
           **What the panel keeps is decided in code, not by a pattern.**
           Every log line carries a LogSource:
             Daemon    sessions, resolution, rolls, created/started/stopped/
                       armed, anomalies, rejects, halts, the kill switch
             Strategy  a strategy's commentary on its own quoting, through
                       StrategyHooks::log
             Wire      the raw FIX log, and the one-line summary of each
                       order and cancel OeClient sends
           The panel takes Daemon, plus anything at Warn or Error whatever
           its source - so a strategy that *cannot* quote still reaches it,
           and so does a mass cancel. The log file still gets all of it.
           This replaced an earlier filter that matched on the "<< " and
           ">> " prefixes, which missed "sending order" and "sending cancel"
           entirely: those are logged by the order client, not by a
           strategy, and a market maker re-quoting both sides writes two of
           them a second. A browser run is what caught it.
           Deliberately not in the panel: fills. They are not logged at all
           today, only counted, and the operator chose to leave the panel to
           lifecycle and problems. Positions is where a fill shows.

GUI-Q29 Fixed columns, and the three buttons under one of them
-----------------------------------------------------------------------------
Question : The operator wants fixed columns, with Start Feed, Start and Stop
           all under a Buttons column and the rest as they are.
Answer   : RESOLVED 2026-10-29. The section is one CSS grid:
             Buttons | Kind | Symbol | Spread | Qty | Max Inventory |
             Requote Threshold | Withdraw Before | Ticks
           with one header row, and every live row and every blank row
           drawn into that same grid.
           **One grid, not a grid per row.** The wrappers - the two row
           containers, each row, each row's field block - are
           `display: contents`, so every cell is an item of the one grid.
           That is what makes a column a column: the browser sizes it once
           across all rows and cannot drift it. The previous layout padded
           each row's controls to a fixed width and got close, but a blank
           row's selects are not the same width as a live row's boxes, so
           they never quite lined up. A browser run now measures every
           cell's left edge against the header's and they match exactly.
           The three buttons are one cell of the Buttons column rather than
           three columns. A blank row's `×` sits in that same cell, so the
           column is as wide as the widest row and the rest align to it.
           **The per-row labels are gone.** They are the header now, once,
           and each row is a single line of boxes. A field's help is still
           its tooltip. A row and the line under it are two lines where
           they used to be three.
           **The columns come from the schema**, as the form always did:
           the union of every registered kind's parameters, each name once,
           in schema order. With one kind that is just its schema; with two
           they share the columns they have in common and leave each
           other's cells empty, so a second kind cannot shear the grid. The
           template is written from that list - the text column takes the
           slack, the rest are as wide as their heading or their box.

GUI-Q30 When may a strategy's parameters be changed?
-----------------------------------------------------------------------------
Question : The operator wants the parameters editable while only the feed is
           running, and locked once the algo is quoting. Where exactly is
           that line, and what happens to the running instance?
Answer   : RESOLVED 2026-10-29. **Armed is the line**, chosen by the operator
           over the two alternatives.
             - Editable: created (Start Feed, quoting nothing) and Running
               but disarmed - the state a strategy is watched in before it
               is trusted.
             - Refused: armed, Stopping, and after a halt.
           Armed is the operator's confirmed intent to quote the parameters
           they were shown (GUI-Q8), so changing them underneath would put a
           different order in the market than the one that was approved. The
           loop is disarm, retune, arm again, and it costs nothing at the
           venue because a disarmed strategy is not quoting.

           **The instance is rebuilt**, not re-pointed, exactly as roll()
           does it: every strategy here reads its parameters once, at
           construction. Same id, same symbols, same arming, counters
           carried over so "placed" does not fall to zero because a width
           changed. A build that the schema refuses changes nothing: the old
           instance is still running when the refusal is returned.

           **The symbol is not editable.** It may be sent - the form shows
           it, and for a rolling strategy it shows the series while the
           strategy is on a window of it - but it may not differ from what
           the strategy already has. Moving a strategy means a subscription,
           a REST resolution and the one-strategy-per-symbol claim (GUI-Q6),
           which is what create and roll are for.

           **A resting order is cancelled first.** Disarmed does not mean
           empty-handed: a disarm leaves what was resting to be taken off
           deliberately, and the instance that placed it is about to go. So
           update() withdraws before it swaps - a cancel, not an abandon,
           because the market is open and the venue will not do it for us
           (the mirror of R-N2/OE-Q6). The reports for those cancels arrive
           after the swap and are matched by nobody, exactly as at a roll;
           the position and the reconciler still see them, and a cancel
           reject still halts.

           Both operator surfaces have it: `POST /api/strategies/{id}/params`
           for the page, `set ID name=value ...` on the stdin console.

=============================================================================
D. NOT QUESTIONS, BUT THINGS G1-G2 MUST NOT FORGET
=============================================================================

GUI-N1  crypto_mm never wired up FeedMonitor
-----------------------------------------------------------------------------
market_data/ has FeedMonitor, which raises FeedHalt on a gap, a stale book, a
reject or a disconnect - the whole of instructions amendment 4. crypto_mm's
main() registers MarketState::on_anomaly and logs anomalies as warnings, but
never constructs a FeedMonitor, so a stale or gapped feed does not currently
stop it. The daemon must wire it, and its halt must be daemon-wide per GUI-Q4.
This is a pre-existing gap in the strategy binary, not something the GUI
introduces.
DONE 2026-10-28 (G2): Trader wires FeedMonitor and routes its FeedHalt through
request_halt(), so market data is fail-stop for the first time. Verified by
Trader.AStaleFeedHaltsEverythingAndTheDaemonStaysUpToSayWhy and by hand against
md_sim. crypto_mm the binary still has no FeedMonitor: it is a one-shot dry-run
tool with a --duration, and the daemon is what runs unattended.

GUI-N2  SIGHUP
-----------------------------------------------------------------------------
crypto_mm blocks SIGINT and SIGTERM and withdraws on either. Closing
PowerShell sends SIGHUP, which is default-terminate, so an SSH drop would kill
a strategy without withdrawing. CancelOnDisconnect::ApiKey is the backstop and
would clear the orders, but the daemon must handle SIGHUP as SIGTERM anyway,
and the docs must say to run it detached.
DONE 2026-10-28: both cpm_trader and crypto_mm block SIGHUP with SIGINT and
SIGTERM and withdraw on any of them (G1 for crypto_mm, G2 for the daemon).

GUI-N3  A long-lived process needs evict_finished()
-----------------------------------------------------------------------------
MarketState::evict_finished() exists because the sandbox lists on the order of
a hundred rolling windows a day ([MD] O2/O6), each holding a book, a lifecycle
history and up to 1024 trade ids. A 60-second crypto_mm run never needed it
and never calls it. A daemon meant to stay up for days must call it on a timer.
DONE 2026-10-28 (G2): Trader::tick() calls it every evict_every (60 s) for
instruments finished longer than evict_finished_after (15 min).
