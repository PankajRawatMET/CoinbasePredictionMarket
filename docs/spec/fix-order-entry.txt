  Introduction
  The Coinbase Prediction Markets (CPM) FIX order-entry gateway implements FIX 5.0 SP2
  (FIXT 1.1) for order submission, cancellation, and execution reporting on binary-outcome
  prediction markets.

  Each FIX session maps 1-to-1 to a registered trading user. The user is resolved from
  SenderCompID(49), which is the API key. There is no separate API-key field in the Logon
  body.

  A second Logon for the same user disconnects the first session with Logout(5),
  Text(58)="replaced by newer connection".

           ⚠️ Sequence Numbers Send ResetSeqNumFlag=Y on Logon to reset sequence
           numbers. Sequence numbers are not guaranteed to persist across a reconnect.

               The API key is carried in the standard header field SenderCompID(49) (see Standard
               Header), not in a Logon-body field.

               Credential validation. Every Logon is fully authenticated before the session is established:

                  1.​ SenderCompID(49) must resolve to a known API key.
                  2.​ Password(554) must be non-empty and match the API key's stored passphrase.
                  3.​ The signature in Text(58) (or RawData(96)) must be a valid HMAC-SHA256 over the
                      signature payload — a 44-character Base64 encoding of a 32-byte digest — and must
                      verify against the API key's secret in constant time.
          4.​ SendingTime(52) must be within the ±30-second signature window (see below).
          5.​ The resolved trading user must be ACTIVE and carry the TRADE permission, and its
              firm/FCM scope must resolve.

       Any failure rejects the Logon (the gateway responds with Logout(5) and closes the
       connection); a bad passphrase, an incorrect or malformed signature, an unknown/disabled key,
       a missing TRADE permission, and a stale SendingTime are all rejected.

            ⚠️ Send real credentials. Password(554) must be your actual API key
            passphrase and Text(58) / RawData(96) a correctly computed HMAC-SHA256
            signature. Placeholder or dummy values are rejected.

       Signature payload
       The signature is an HMAC-SHA256 over four values concatenated with no separators,
       encoded UTF-8:


         None
         payload = SendingTime + ApiKey + TargetCompID + Password

                      Identifier handling
                      ExecID(17), OrderID(37), MassActionReportID(1369) and
                      MarketSettlementReportID(20105) are all FIX STRING fields. Each value is the base-10
                      text form of a 64-bit integer — ASCII digits only, with no decimal point, sign, or separators.
                      Despite looking numeric, treat them as opaque strings:

                          -​    Do not parse into a 32-bit integer. These values grow with exchange activity and will
                                exceed the range of a signed 32-bit type. If you must hold them numerically, use a 64-bit
                                type.
                          -​    Compare for equality as strings. Echo them back byte-for-byte — for example
                                OrderID(37) on OrderCancelRequest(35=F), or an ExecID as an
                                EventResendRequest(35=F3) bound.
                          -​    Ordering is only meaningful for ExecID and the two report IDs, which share one
                                increasing number space. Compare them numerically with a 64-bit type when you need
                                ordering; do not assume consecutive values, since the space is not contiguous.
                          -​    Do not derive meaning from the digits. The internal composition is not part of the
                                contract and may change.

                      These are not FIX PRICE or QTY values: there is no scale, no fractional part, and no rounding.
                      Contrast Price & Quantity Encoding, which does use decimal values.

                      0 appears as a sentinel where no identifier exists — see the individual field descriptions.

              Side semantics. The FIX gateway accepts only 1=Buy and 2=Sell, and both are expressed
              against the YES contract — Side(54)=SELL(2) is sell YES, not buy NO. There is no NO-side
              order entry on FIX; convert client-side: BUY_NO at P ≡ SELL YES at 1.000 − P.

              Missing Parties. An order without a PartyRole(452)=CUSTOMER_ACCOUNT(24) entry, or
              with an empty PartyID, is rejected with BusinessMessageReject(j),
              Text(58)="INVALID_SUBACCOUNT: Parties with PartyRole=24
              (CUSTOMER_ACCOUNT) is required". Sub-accounts are created lazily on first use, so an
              unrecognized sub-account string is not itself an error.

              ClOrdID character set. Use printable ASCII only. The limit is 16 bytes, which for ASCII is
              exactly 16 characters. Non-ASCII is not supported: such a value is either rejected or
              round-tripped back to you altered, and it consumes more than one byte per character against
              the limit. Do not send multi-byte characters in this field.

 Primary order lifecycle event. The ExecType(150) field identifies what triggered this report.

 ExecType Values


Code                                               Description

A — PendingNew                                     Order accepted but held for the instrument's
                                                   configured speed-bump delay, so not yet
                                                   matchable. Only on instruments with a speed
                                                   bump; a further report follows on release.

0 — New                                            Order accepted, resting on book

4 — Canceled                                       Order canceled (user request, mass cancel,

8 — Rejected                                       Order rejected by the exchange

F — Trade                                          Partial or full fill

C — Expired                                        See below — has two distinct causes


       ⚠️ ExecType(150)=EXPIRED(C) has two causes
            1.​ An IOC remainder. An IOC order fills what it can and its unfilled remainder
               is canceled with reason TIME_IN_FORCE, terminating as
               ExecType(150)=EXPIRED(C) / OrdStatus(39)=EXPIRED(C) — and
               not ExecType(150)=CANCELED(4). See the exception below.
            2.​ An FOK that cannot fill. FOK is all-or-nothing and never leaves a remainder
                — the exchange checks whether the whole quantity is available before
                matching anything. If it is not, nothing executes and the order terminates as
                         ExecType(150)=EXPIRED(C) / OrdStatus(39)=EXPIRED(C) with
                         Text(58)="FOK_NOT_FILLED".

                  Exception — a cancel you asked for reports Canceled, not Expired. Cancelling
                  an order you have not yet received an ExecutionReport for looks the same as
                  cancelling any working order: you receive the fills (if any) that occurred before the
                  cancel took effect, then an ExecType(150)=CANCELED(4) report for the unfilled
                  quantity — not EXPIRED(C), because that quantity went away at your request
                  rather than through natural time-in-force expiry.

                  Every other rejection, including MAX_EXECUTION_COST_EXCEEDED, reports
                  ExecType(150)=REJECTED(8) / OrdStatus(39)=REJECTED(8).

    Self-Match Prevention
    Self-Match Prevention (SMP) prevents a trading user from inadvertently trading against their
    own open orders. SMP is opt-in and is configured at the user and firm level;

            ℹ️ SMP ID Validation The SelfMatchPreventionId(7928) on an order must
            match the SMP ID registered for the trading user. If the IDs differ, the order is
            rejected with Text(58)="INVALID_FIELD_VALUE" and
            OrdRejReason(103)=OTHER(99). Set SelfMatchPreventionId to NULL (omit the
            field) to opt out of id-based SMP for a specific order.

    SelfMatchPreventionStrategy (8000) Values


Code                                                     Description

N                                                        Cancel Aggressing — the incoming order is
                                                         canceled; the resting order remains on book

O                                                        Cancel Resting — the resting order is canceled;
                                                         the aggressor continues matching remaining
                                                         liquidity

Q                                                        Cancel Both — both the aggressor and the
                                                         matched resting order are canceled


    Mode resolution. Two independent SMP paths exist:

       -​    Firm-level: fires when the aggressor and resting order share both the same firm and the
             same sub-account. Uses the firm's configured default mode. This path needs no SMP
             tags on the order at all.
       -​    ID-based: fires when both orders carry the same positive SelfMatchPreventionId.
             Uses the aggressor's SelfMatchPreventionStrategy(8000) if present, and
             defaults to O (Cancel Resting) when omitted.

    An SMP cancel arrives as ExecutionReport(8) with ExecType(150)=CANCELED(4),
    ExecRestatementReason(378)=CANCEL_SELF_MATCH_PREVENTION(7), and
    Text(58)="SELF_MATCH_PREVENTION".
    Cancel on Disconnect
    Cancel-on-disconnect (COD) is opt-in per session via CancelOrdersOnDisconnect(8013)
    on Logon(A). When the session drops, the exchange cancels the user's resting orders
    according to the scope you selected.

    Scope values (tag 8013)


Code                               Name                                Effect on disconnect

N                                  NO_CANCEL                           No cancellation — resting orders
                                                                       survive the drop. This is also the
                                                                       default when 8013 is absent.

Y                                  CANCEL_FOR_SESSION                  Cancel the disconnecting
                                                                       session's orders.

A                                  CANCEL_FOR_API_KEY                  Cancel all of the API key's active

    Behavior

       -​   The scope is fixed at Logon and applies for the life of the session.
       -​   Cancellation fires only on a genuine client disconnect. When a newer connection for
            the same API key replaces this session (see Connection & Session), the API key is still
            live, so no cancel-on-disconnect is triggered — the replaced session's orders remain.
       -​   Each canceled order is reported as ExecutionReport(8) with
            ExecType(150)=CANCELED(4), OrdStatus(39)=CANCELED(4),
            ExecRestatementReason(378)=CANCEL_ON_DISCONNECT(1), and
            Text(58)="CLIENT_DISCONNECT". Because the session that placed the orders has
            disconnected, these reports are recoverable through Event Resend after reconnecting.

    Send the scope you actually want on every Logon rather than relying on the default, and do not
    send Y or A unless you intend cancel-on-disconnect.




    Event Resend (F3)
    The exchange retains recent outbound events per trading user. You can request replay of a
    range by ExecID to recover missed messages without rebuilding state from scratch.
Replayable message types: ExecutionReport(8), OrderCancelReject(9),
OrderMassCancelReport(r), MarketSettlementReport(UMS).
BusinessMessageReject(j) and mass-cancel rejects raised on receipt are not stored.

Key Behaviors

   -​   Replayed messages carry PossResend(97)=Y in the header. PossDupFlag(43) is
        not set.
   -​   TransactTime(60) is the original event timestamp, preserved exactly. Only the
        session header (MsgSeqNum(34), SenderCompID(49), TargetCompID(56),
        SendingTime(52)) is re-stamped. Use PossResend, not TransactTime, to
        distinguish replayed from live events.
   -​   Replayed messages do consume outbound FIX sequence numbers — they are new
        messages with a fresh MsgSeqNum, not a FIX-session gap fill. That is precisely why
        PossResend is used rather than PossDupFlag.
   -​   Replay is sequential, in ascending ExecID order.
   -​   "Everything since X" semantics — BeginExecId need not match a stored event
        exactly. The request is rejected only when [BeginExecId, EndExecId] overlaps no
        stored event.
   -​   Only one resend at a time per user; a concurrent EventResendRequest(F3) is
        rejected with
        EventResendRejectReason(22006)=RESEND_ALREADY_IN_PROGRESS(3).
   -​   A mid-stream delivery failure demotes the terminating EventResendComplete(F4) to
        EventResendReject(F5) with reason 5 (Server Error).

Retention. The current window is up to 24 hours, and is a present limit rather than a
contract — it is expected to be extended in a future release. Today it is not guaranteed: the
usable window can be shorter without notice, and history may be lost, after which F3 rejects
with EventResendRejectReason(22006)=BEGIN_EXEC_ID_TOO_SMALL(1) until new
events accumulate.

Treat 24 hours as a ceiling, not an allowance. Anchor recovery on your last-processed ExecID
and reconcile promptly after reconnecting rather than deferring replay, and do not rely on Event
Resend as an audit or system-of-record facility.

Session-level gap fill is separate. Standard FIX ResendRequest(2) retransmission is
supported and is the correct tool for filling a MsgSeqNum gap. F3 replays business events by
ExecID and does not fill sequence gaps.
