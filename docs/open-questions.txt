Q8  L1 (264=1) behaviour when the best price moves
-----------------------------------------------------------------------------
Question : When the best YES/NO bid moves to a new price, does the server send
           a Delete of the old level plus a New level, or a single Change
           carrying the new price?
Spec ref : PDF p.106-107, MD:449-529  L1 subscribe, snapshot and delta examples.
           The delta example only shows a size change at the same price
           (0.560: 333.00 -> 200.00), MD:521-523.
           PDF p.103, MD:317-318  "Replace the level with this value ... A size
                                   of 0.00 removes the level."
Proposal : The L1 book holds one level per side, and any update for that side
           replaces it. A size of 0 empties that side.
Status   : CONFIRMED 2026-10-26 by O9: exactly as proposed. A size change at
           the same best price is one 279=1 (236 messages); a new best price is
           279=2 delete of the old best THEN 279=0 new (92 messages). No other
           pattern occurred.

Q9  Crossed / locked book definition
-----------------------------------------------------------------------------
Question : Both sides are bids (YES bids and NO bids). What exactly counts as
           crossed?
Spec ref : PDF p.100, MD:192  "1 Ask - Order book - NO bids"
           PDF p.107, MD:496  "best NO bid 0.380 ... -> yes_ask = 0.620"
                              (so implied YES ask = 1.000 - best NO bid)
           The spec has no crossed-book rule.
Proposal : crossed if best_yes_bid + best_no_bid > 1.000
           locked  if best_yes_bid + best_no_bid = 1.000
           Both flag the book as suspect (reported, not auto-fixed).
Status   : ADOPTED 2026-10-23, STILL UNOBSERVED as of O9: over 1142 book
           entries the top-of-book sum never exceeded 0.990, so the rule has
           never been violated, but neither has it been exercised. The check
           stays in, and stays an assumption.

Q24 Gap recovery: resubscribe, or reconnect the session?
-----------------------------------------------------------------------------
Question : A MsgSeqNum gap means market data was lost. Does recovery tear the
           session down and log on again, or keep it and resubscribe?
Spec ref : PDF p.97, MD:82     ResendRequest/SequenceReset listed, behaviour
                               not described.
           PDF p.41 [WS]       "If you detect a gap, you should unsubscribe
                               and resubscribe" (no reconnect mentioned).
           Q12 (DECIDED)       "On a gap: reconnect with 141=Y, resubscribe."
           [OBS O10]           the session stayed healthy for 20 minutes while
                               one subscription was silent: session health and
                               data health are independent.
Proposal : Resubscribe on the live session for a gap; reconnect only when the
           session itself drops. A gap fill resolves the sequence, so the
           session is fine and only the data is missing. This narrows Q12,
           which is a decision of yours rather than anything the spec says.
Status   : RESOLVED 2026-10-26 - NEITHER. A gap stops the strategy, and
           stopping the strategy stops the feed. No automatic recovery: the
           client detects the gap, marks the affected books invalid, reports a
           terminal halt and stops the session. This supersedes Q12's
           "reconnect with 141=Y, resubscribe" and the original Stage 5
           instruction to rebuild from a fresh snapshot.

Q25 Default stale-feed threshold
-----------------------------------------------------------------------------
Question : How long must a subscription be silent before it is rebuilt?
Spec ref : Not in the spec.
           [OBS O3/O4]  sandbox quotes live 15-16 s, so a thin book is
                        genuinely quiet for that long.
           [OBS O10]    a settled instrument is silent forever, by design.
Proposal : 30 s, configurable with --stale-secs. Below ~20 s a thin book would
           false-positive.
Status   : RESOLVED 2026-10-26 - a stale feed stops the strategy, so the
           threshold default of 30 s was confirmed 2026-10-26 ("go with
           defaults"), overridable with --stale-secs.
           Originally:
           threshold is a halt trigger rather than a recovery trigger. The
           30 s default and --stale-secs stand unless you say otherwise.
           CONSEQUENCE: the detector MUST exclude instruments that are
           Closed, Determined or Settled. Those are silent by design [OBS
           O10], so a detector that ignored lifecycle state would halt the
           strategy at every 15-minute window roll.

Q26 Does recovery follow a rolled window's successor?
-----------------------------------------------------------------------------
Question : When a 15-minute window closes, the successor is announced on the
           lifecycle feed (O6/O10). Should the supervisor subscribe the
           successor's book automatically?
Spec ref : Not in the spec. [OBS O6] new windows arrive as 326=21 then 326=17.
Proposal : No. Recovery repairs the subscriptions you asked for; deciding what
           to follow is strategy policy, and belongs above the market data
           library.
Status   : ADOPTED 2026-10-26 - "go with defaults". Nothing follows a
           successor; the lifecycle feed still reports it (O6/O10) so a
           strategy can.

Q27 Which reject codes are retryable?
-----------------------------------------------------------------------------
Question : A resubscribe can be rejected. Which 281 codes should stop us
           retrying that symbol?
Spec ref : PDF p.111 (281 codes); [OBS O6] a settled instrument is already
           "281=0 unknown symbol" about 2 minutes after it settles.
Proposal : 281=0 (unknown symbol) drops the symbol permanently: it is gone,
           not broken. 281=1 (duplicate MDReqID) retries once with a fresh id.
           281=4/5/8/9 are client bugs, so they are logged and the
           subscription is abandoned rather than retried in a loop.
Status   : RESOLVED 2026-10-26 - NONE are retried. Any reject (Y or j) stops
           the strategy, whatever the code. No taxonomy is needed.
           NOTE: a subscribe sent within ~2 minutes of a window closing is
           answered 281=0 unknown symbol [OBS O6], so under this rule a
           mistimed subscribe at a window boundary halts the strategy. See
           Q29.

Q28 Does a disconnect also stop the strategy?
-----------------------------------------------------------------------------
Question : Q24/Q25/Q27 cover gaps, stale feeds and rejects. A TCP disconnect
           or a server Logout is a fourth case. QuickFIX reconnects on its own
           every ReconnectInterval (30 s) and re-sends a signed Logon, so
           unless the initiator is actively stopped the session comes back up
           WITHOUT any subscriptions (Q22) and therefore with no data.
Spec ref : PDF p.41 [WS]  "If your connection drops, you must reconnect,
                           re-authenticate, and resubscribe".
Proposal : Treat it like a gap: halt. A disconnect means data was missed, and
           a silently re-established session with no subscriptions is worse
           than a stopped one. The halt stops the initiator so QuickFIX cannot
           quietly log back on.
Status   : ADOPTED 2026-10-26 - "go with defaults". Implemented, with one
           consequence found while building it: the owner's own stop() causes
           a logout, which arrives as a Disconnect on the session's thread. A
           halt is therefore never delivered after FeedMonitor::stop(), or it
           re-enters the halt handler there and deadlocks. See design.md §15.

Q29 A reject on the very first subscribe
-----------------------------------------------------------------------------
Question : Should a reject while subscriptions are still being established be
           treated differently from one that arrives mid-run? Starting a
           strategy seconds before a window rolls would halt it immediately
           with 281=0, before it ever had data.
Spec ref : [OBS O6] a settled instrument is "unknown symbol" ~2 min after it
           settles.
Proposal : No difference: halt either way, since a strategy that cannot
           subscribe what it was told to subscribe should not run. The
           operator restarts it with a live symbol.
Status   : ADOPTED 2026-10-26 - "go with defaults". A subscribe within ~2 min
           of a window closing halts the run with 281=0; restart with a live
           symbol (md_client --list-instruments names them).
