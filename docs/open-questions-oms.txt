===================================================
Raised 2026-10-26, from docs/spec/fix-order-entry.txt (the Order Entry section
of docs/spec/cpm-api-spec.pdf). Same format as docs/open-questions.txt: each
entry carries the question, the spec reference, and the proposed answer, which

References:

A. BLOCKING STAGE 1
=============================================================================

OE-Q1  Sandbox endpoint for order entry
-----------------------------------------------------------------------------
Question : What host and port, and is it TLS? The spec gives "Default Port
           6110" and no host, exactly as it gave none for market data.
Spec ref : OE:193 area (Connection & Session: Transport TCP, port 6110)
           [MD] the market data sandbox turned out to be
           fix-marketdata.cpm-sandbox.fairx.net:6120 over TLS even though the
           spec said plain TCP (Q23).
Note     : 2026-10-26 creds-oe.env reuses the market data sandbox HOST with
           port 6110 as the working guess, and carries the market data
           credentials for now. Stage 0 (dictionaries) does not need this
           answered; Stage 1 cannot connect without it.
Proposal : Assume the market data sandbox host on port 6110 over TLS by
           analogy, but DO NOT connect until you confirm the host. The
           endpoint guard refuses anything that is not the sandbox, as the
           market data client does. Nothing is sent to a live venue without
           you saying so explicitly.
Status   : RESOLVED 2026-10-26 - you supplied it, and it is CONFIRMED working
           (OE-O1): host fix-order.cpm-sandbox.fairx.net, port 6110, TLS.
           Note the name is "fix-order", not the "fix-orderentry" this document
           guessed. Two consequences for Stage 1:
             (a) the endpoint guard in shared/common hardcodes one sandbox host
                 (kSandboxHost, the market data one), so it must become
                 per-service: the market data config accepts only the market
                 data host and the order entry config only this one. That is
                 stricter than a shared allowlist and means neither client can
                 ever be pointed at the other gateway.
             (b) TLS is required, and the CA file defaults to the system trust
                 store, with CPM_OE_CA_FILE as an override - the same as market
                 data, which needs no CA file set.

OE-Q2  Sub-account PartyID to use
-----------------------------------------------------------------------------
Question : Every NewOrderSingle needs a Parties entry with PartyRole=24 and a
           sub-account PartyID. Which value should the client send?
Spec ref : OE:452-470 (Parties required; "INVALID_SUBACCOUNT: Parties with
           PartyRole=24 (CUSTOMER_ACCOUNT) is required"); sub-accounts are
           created lazily on first use, so an unknown string is not an error.
Proposal : From the environment (CPM_OE_SUBACCOUNT), validated client-side
           against the spec's charset and length rules before sending.
Status   : RESOLVED 2026-10-26 - you do not need an existing sub-account. The
           spec is explicit (OE:492): "Sub-accounts are created lazily on first
           use, so an unrecognized sub-account string is not itself an error."
           So this was a naming decision, not a prerequisite.
           CPM_OE_SUBACCOUNT=dev-1 is set in creds-oe.env; change it if you
           want another name, because the FIRST order that names it creates it
           on the account.
           The name's character set depends on its length (OE:470-485), and the
           bands are now checked client-side by check_subaccount() so a bad one
           is caught before the round trip rather than coming back as
           BusinessMessageReject(j) "invalid PartyID" - which under OE-Q6 would
           halt the run:
             1-18   any printable ASCII
             19-20  alphanumerics and '-' only
             21-31  lowercase hex, no leading '0'
             32-35  invalid
             36     a lowercase canonical UUID
             >36    invalid

OE-Q3  The Logon example contradicts the Logon field table
       [ADOPTED 2026-10-26 - "go with defaults": 49 only, no 20001]
-----------------------------------------------------------------------------
Question : The normative text says the API key travels only in
           SenderCompID(49) and that there is "no separate API-key field in
           the Logon body". The worked example sends 20001=my-access-key.
Spec ref : OE:196-200 ("The API key is carried in the standard header field
           SenderCompID(49) ... not in a Logon-body field")
           OE:1427 (example: 1137=9|20001=my-access-key|554=...)
Proposal : Follow the normative text: 49 only, no 20001. Keep 20001 ready to
           add if the sandbox rejects the Logon, and record what happened -
           the market data signing recipe was settled the same way (Q2 [MD]).
Status   : RESOLVED 2026-10-26 by observation (OE-O1): a Logon carrying the API
           key in SenderCompID(49) ONLY, with no 20001 anywhere, was accepted
           by the live gateway. The spec's example is wrong, exactly as its
           market data counterpart was. 20001 stays undefined in the
           dictionary.

OE-Q4  Cancel-on-disconnect scope, CancelOrdersOnDisconnect(8013)
       [ADOPTED 2026-10-26 - "go with defaults": A, see creds-oe.env]
-----------------------------------------------------------------------------
Question : N (no cancel, the default), Y (cancel this session's orders) or A
           (cancel all the API key's orders) on every Logon?
Spec ref : OE:1340-1375. Fires only on a genuine disconnect; a newer
           connection replacing the session does NOT trigger it, so the
           replaced session's orders stay live. Each cancel arrives as
           ExecType=4 with ExecRestatementReason=1 and Text="CLIENT_DISCONNECT",
           recoverable later through Event Resend.
Proposal : A (CANCEL_FOR_API_KEY) while developing and testing: an
           unreconciled process should not leave resting orders in the market.
           Configurable, and the choice is logged at Logon.
Status   : PROPOSED.

OE-Q5  Settlement reports, ReceiveSettlementReports(20127)
       [ADOPTED 2026-10-26 - "go with defaults": Y, see creds-oe.env]
-----------------------------------------------------------------------------
Question : Opt in to MarketSettlementReport (UMS) pushes?
Spec ref : OE:1040-1100. Pushed per (firm, instrument) at settlement, to every
           connected session of the firm.
Proposal : Y. With no positions API, UMS is the only server-side position and
           payout figure we ever receive.
Status   : PROPOSED.

C. AFFECTING THE STATE MACHINE AND RECOVERY
=============================================================================

OE-Q6  Does the market data fail-stop rule carry over to orders?
-----------------------------------------------------------------------------
Question : For market data you chose: gap, stale feed or any reject stops the
           strategy (Q24/Q25/Q27 [MD]). Order entry is different, because
           stopping leaves resting orders in the market that nobody is
           watching. On a gap or disconnect, which of these?
             (a) rely on cancel-on-disconnect to flatten (OE-Q4 = Y or A),
                 then stop;
             (b) reconnect, mass cancel (q), reconcile with F1/F3, then stop;
             (c) reconnect, reconcile with F1/F3, and continue trading.
Spec ref : OE:1376-1440 (Event Resend, "anchor recovery on your
           last-processed ExecID and reconcile promptly")
           OE:1340-1375 (cancel-on-disconnect)
Proposal : (b). Cancel is cheap, exempt from the rate throttle, and covers
           orders you have not yet seen a report for; reconciling afterwards
           then tells you what actually happened. Submission stays blocked
           until reconciliation finishes either way.
Status   : RESOLVED 2026-10-26 - "go with defaults": (b). On a gap or a
           disconnect the client reconnects, mass cancels (q), reconciles with
           F1/F3 from the durable bookmark, and then stops. It never resumes
           submitting on its own. Market data's fail-stop is therefore
           preserved in spirit: the run still ends, but it ends flat.

OE-Q7  A durable ExecID bookmark
-----------------------------------------------------------------------------
Question : Market data persists nothing by design. Order management needs the
           last processed ExecID across restarts, or F3 replay has no anchor.
           May the process write a small bookmark file?
Spec ref : OE:1376-1440 (F1/F3 recovery flow, 24-hour retention which is "a
           present limit, not a contract")
Proposal : Yes: one small file holding the last processed ExecID and the
           ClOrdID counter, flushed as events are processed. It is the minimum
           durable state an order manager can have.
Status   : RESOLVED 2026-10-26 - "go with defaults": allowed. The original "no
           persistence" constraint stays in force for market data and for the
           FIX message store (still null/in-memory); this bookmark is the only
           file the order manager writes. Recorded as project instructions
           amendment 6.

OE-Q8  Excess decimal precision: truncate, where market data rejects
       [ADOPTED 2026-10-26 - "go with defaults": truncate on inbound OE]
-----------------------------------------------------------------------------
Question : The order entry gateway truncates excess precision toward zero
           ("44=0.6505 is accepted and becomes 0.650"). The market data parser
           rejects it (Q11 [MD]). Which behaviour for inbound order entry?
Spec ref : OE:390-400 ("Parse decimals tolerantly ... Excess precision is
           truncated toward zero, not rejected")
Proposal : Match the venue: truncate on inbound order entry, keep rejecting on
           market data, and add a truncating variant beside
           cpm::parse_scaled rather than changing it. Outbound always emits
           exact scale.
Status   : PROPOSED.

OE-Q9  ClOrdID scheme
       [ADOPTED 2026-10-26 - "go with defaults": prefix + base36 counter, persisted]
-----------------------------------------------------------------------------
Question : ClOrdID must be unique among the user's live orders, at most 16
           printable ASCII bytes, and usable to cancel an order whose OrderID
           we have not yet seen - including after a restart.
Spec ref : OE:400-410, OE:520-530 (16 bytes, printable ASCII, uniqueness)
Proposal : <prefix><base36 counter>, e.g. "A7F3K2" + counter, with the prefix
           from configuration and the counter persisted with the bookmark
           (OE-Q7). Never reuses a value within the retention window.
Status   : PROPOSED.

OE-Q10 Client-side rate limiting
       [ADOPTED 2026-10-26 - "go with defaults": 10 orders/sec, cancels unthrottled]
-----------------------------------------------------------------------------
Question : The spec says cancels are "exempt from the session rate throttle"
           but never states the throttle itself.
Spec ref : OE:623-626
Proposal : A client-side token bucket, conservative by default (10 orders per
           second), cancels unthrottled, configurable, and server rejects
           surfaced rather than hidden.
Status   : PROPOSED.

OE-Q11 Positions, with no positions API
       [ADOPTED 2026-10-26 - "go with defaults": derived from fills, reconciled at settlement]
-----------------------------------------------------------------------------
Question : Nothing in the documented API returns open orders, positions or
           balances. How should positions be maintained?
Spec ref : REST sections 3-6 are reference data only; UMS is firm-instrument
           granularity at settlement (OE:1040-1100).
Proposal : Derive positions per (symbol, sub-account) from fills, flag them as
           derived rather than confirmed, and reconcile against UMS at
           settlement. Report any mismatch loudly - it means we missed a fill.
Status   : PROPOSED.

OE-Q12 Market orders
       [ADOPTED 2026-10-26 - "go with defaults": supported, opt-in per order]
-----------------------------------------------------------------------------
Question : Should the client send OrdType=1 at all? The venue converts it to
           an IOC at the worst admissible price (BUY 0.999 / SELL 0.001).
Spec ref : OE:500-515
Proposal : Support it but require an explicit opt-in per order, because on a
           thin prediction market an unpriced aggressive order can fill very
           far from the touch. A priced IOC is the safer default.
Status   : PROPOSED.

OE-Q13 Both rejection paths are terminal
-----------------------------------------------------------------------------
Decision : A BusinessMessageReject(j) with no ExecutionReport and an
           ExecutionReport with 150=8 are both terminal for that ClOrdID. The
           state machine treats them identically and branches on OrdStatus(39)
           and OrdRejReason(103), never on Text(58), which the spec warns is
           not a stable contract (OE:950-960).
Status   : DECIDED.

OE-Q14 NO-side orders are converted client-side
-----------------------------------------------------------------------------
Decision : FIX takes only Buy/Sell of YES. The OMS exposes NO-side intent and
           converts: BUY_NO at P becomes SELL YES at 1.000 - P, matching how
           the market data book already treats both sides as bids
           (docs/design.md section 8).
Status   : DECIDED (OE:478-482).

OE-Q15 Identifiers stay strings
-----------------------------------------------------------------------------
Decision : ExecID(17), OrderID(37), MassActionReportID(1369) and
           MarketSettlementReportID(20105) are kept as strings, compared for
           equality as strings and echoed byte for byte; only ordering uses a
           64-bit numeric comparison, and no meaning is derived from the
           digits - the spec's own example comment "(seqId << 1) | sideBit"
           contradicts its rule, so the rule wins (OE:330-350).
Status   : DECIDED.

OE-Q16 Price tick validation stays server-side
-----------------------------------------------------------------------------
Decision : The client validates 3 decimal places and the 0.001-0.999 range,
           and lets the venue reject tick violations (103=18
           INVALID_PRICE_TICK). The tick structure per instrument comes from
           REST (O5 [MD]), which is out of scope.
Status   : DECIDED.

OE-Q17 Drop copy is out of scope
-----------------------------------------------------------------------------
Decision : The drop-copy gateway (TargetCompID CBPMDC, read-only
           ExecutionReport + UMS with F1/F3 replay) is recorded in
           docs/spec/fix-dropcopy.txt and left for later. It is the audit
           path, not a trading path.
Status   : DECIDED.
